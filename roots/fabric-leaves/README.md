# fabric-leaves

This root pushes the EVPN/VXLAN configuration to **every leaf** through the VyOS
HTTPS API. For each leaf, [modules/fabric/leaf](../../modules/README.md#fabricleaf)
builds a list of plain VyOS `set` commands from the inventory, and sends the
whole list as one `vyoscmd_commands` resource named `<leaf>-system`.

Because the output is ordinary VyOS CLI, you can read exactly what will change in
the plan. The command blocks below are excerpts from the real output for the leaf
on venom (ID 17), generated from the current inventory. They're grouped by topic
and commented; the full list for that leaf is about 280 commands.

## Which leaves

| Leaves | Where they come from | Role | Access interface |
| --- | --- | --- | --- |
| `external_l2_01` (42), `external_l3_01` (18), `external_l3_02` (19) | `fabric.leaves` (physical) | as configured | as configured |
| one per host in `nodes.proxmox`: IDs 11–17 and the standalone `greatfox` (20) | generated by `modules/fabric/leaves` | `proxmox` | `eth3` (number of spines + 1) |

The list comes from `modules/fabric/leaves`, which fabric-spines and the
services-config DNS records also use, so all three see the same leaves.

Each leaf's API address is host number *ID* in `fabric.settings.management_prefix`,
so venom's leaf is `https://10.20.10.17`. The API key comes from `vyos_api_key`,
or the `VYOS_API_KEY` environment variable. TLS verification is off, because
VyOS uses a self-signed certificate.

## Which VRFs each leaf gets

A leaf gets every VRF (L3VNI) whose `roles` list includes the leaf's role, and
all the VLANs (L2VNIs) inside those VRFs. With today's
[`vnis.auto.tfvars`](../../inventory/auto.tfvars/vnis.auto.tfvars):

| Role | Leaves | VRFs (L3VNI) | VLANs |
| --- | --- | --- | --- |
| `proxmox` | `vtep-*` on every host | `lylat_service` (6600), `lylat_lan` (6900), `lylat_infra` (6200), `lylat_ai` (6700) | 2, 6, 8, 9, 10, 11, 12 |
| `external_l2` | `external_l2_01` | `lylat_lan` (6900), `lylat_ai` (6700) | 9, 10, 11, 12 |
| `external_l3` | `external_l3_01`, `external_l3_02` | `lylat_external` (6666) | none (routed only) |

A leaf whose role matches no VRF gets only its interface MAC bindings and the
system settings.

## What gets configured

### 1. Interfaces

```text
# Bind interface names to the NIC MACs that fabric-vms gave the VM.
# (Generated proxmox leaves only; see modules/fabric/macs.)
set interfaces ethernet eth1 hw-id 02:00:00:17:00:01
set interfaces ethernet eth2 hw-id 02:00:00:17:00:02
set interfaces ethernet eth3 hw-id 02:00:00:17:00:03

# Spine links: underlay MTU, plus router advertisements. FRR's link-local
# ("interface") BGP peering relies on RAs to learn the neighbor's address.
set interfaces ethernet eth1 description 'p2p-spine-1'
set interfaces ethernet eth1 mtu '9189'
set service router-advert interface eth1

# Loopback: the VTEP address (IPv6) and the router-ID (IPv4).
set interfaces dummy dum240 address 'fd69:255:240::17/128'
set interfaces dummy dum240 address '10.255.240.17/32'

# Access trunk towards the host's VMs (it joins vmbr4000).
set interfaces ethernet eth3 description 'link to tenant VLANs'
set interfaces ethernet eth3 mtu '9119'
```

### 2. BGP: underlay and overlay

```text
set protocols bgp system-as 700
set protocols bgp parameters router-id 10.255.240.17
# Advertise the VTEP loopback into the underlay; it's the only underlay route this leaf sends.
set protocols bgp address-family ipv6-unicast network fd69:255:240::17/128
# EVPN: advertise every local VNI, and flood BUM traffic by head-end replication (no multicast).
set protocols bgp address-family l2vpn-evpn advertise-all-vni
set protocols bgp address-family l2vpn-evpn flooding head-end-replication
set protocols bgp address-family l2vpn-evpn vni 9008 rd '10.255.240.17:9008'

# One underlay neighbor per spine port (link-local), and one overlay neighbor per spine loopback.
set protocols bgp neighbor eth1 interface v6only peer-group 'spine_underlay'
set protocols bgp neighbor fd69:255:240::1 peer-group 'spine_overlay'

# Underlay: eBGP, shown to the spine as AS 717 (leaf_underlay_as_base 700 + ID 17).
# Export only locally originated routes.
set protocols bgp peer-group spine_underlay remote-as 'external'
set protocols bgp peer-group spine_underlay local-as 717 no-prepend replace-as
set protocols bgp peer-group spine_underlay address-family ipv6-unicast route-map export 'local_as_rm'
set protocols bgp peer-group spine_underlay bfd

# Overlay: iBGP to the spines (route reflectors), sourced from the loopback.
set protocols bgp peer-group spine_overlay remote-as 'internal'
set protocols bgp peer-group spine_overlay update-source 'dum240'
set protocols bgp peer-group spine_overlay address-family l2vpn-evpn route-map export 'RM-EVPN-SPINE-EXPORT'
set protocols bgp peer-group spine_overlay bfd
```

`local-as 717 no-prepend replace-as` lets the leaf run AS 700 for the overlay
while each leaf still looks like its own AS in the underlay. Unique underlay
ASNs prevent eBGP's AS-path loop check from dropping one leaf's loopback at
another leaf.

### 3. VXLAN and the bridge

Each leaf has a single VXLAN device, `vxlan0`, in "external" mode, and one
VLAN-aware bridge, `br0`. Every VNI is a VLAN on `br0`, mapped to its VNI on
`vxlan0`:

```text
set interfaces vxlan vxlan0 parameters external        # one device for every VNI (the single-VXLAN-device model)
set interfaces vxlan vxlan0 parameters vni-filter
set interfaces vxlan vxlan0 parameters nolearning      # MACs are learned from EVPN, not by flooding
set interfaces vxlan vxlan0 source-address 'fd69:255:240::17'
set interfaces vxlan vxlan0 mtu '9119'
set interfaces bridge br0 enable-vlan
set interfaces bridge br0 mtu '9119'                   # br0 and its VLANs use the tenant MTU too
set interfaces bridge br0 member interface vxlan0 disable-learning

# L3VNI of lylat_service: VLAN 66 <-> VNI 6600, placed in the VRF
set interfaces vxlan vxlan0 vlan-to-vni 66 vni '6600'
set interfaces bridge br0 vif 66 vrf 'lylat_service'

# L2VNI: VLAN 8 <-> VNI 9008, and allow VLAN 8 on the access trunk
set interfaces vxlan vxlan0 vlan-to-vni 8 vni '9008'
set interfaces bridge br0 vif 8 vrf 'lylat_service'
set interfaces bridge br0 member interface eth3 allowed-vlan '8'
```

### 4. Anycast gateway (one per VLAN)

```text
# The same IP and MAC on every leaf, so a VM's gateway is always its local leaf.
set interfaces pseudo-ethernet peth9008 source-interface 'br0.8'
set interfaces pseudo-ethernet peth9008 address '10.8.0.5/16'
set interfaces pseudo-ethernet peth9008 mac '02:00:00:00:08:01'
set interfaces pseudo-ethernet peth9008 anycast-gateway
set interfaces pseudo-ethernet peth9008 vrf 'lylat_service'
```

### 5. VRFs and route-targets

```text
set vrf name lylat_service table 1000
set vrf name lylat_service vni 6600
set vrf name lylat_service protocols bgp address-family l2vpn-evpn rd '10.255.240.17:6600'

# EVPN route-targets: what this VRF exports, and which VRFs' routes it accepts.
set vrf name lylat_service protocols bgp address-family l2vpn-evpn route-target export '700:6600'
set vrf name lylat_service protocols bgp address-family l2vpn-evpn route-target import '700:6200'

# Local route leaking between VRFs on this leaf (BGP IPv4 VPN).
set vrf name lylat_service protocols bgp address-family ipv4-unicast route-target vpn export '700:6600'
set vrf name lylat_service protocols bgp address-family ipv4-unicast route-target vpn import '700:6200 700:6900'

# Put connected subnets into BGP, and advertise the VRF's IPv4 routes as EVPN type-5.
set vrf name lylat_service protocols bgp address-family ipv4-unicast redistribute connected route-map 'RM-LYLAT_SERVICE-CONNECTED-TO-BGP'
set vrf name lylat_service protocols bgp address-family l2vpn-evpn advertise ipv4 unicast route-map 'RM-LYLAT_SERVICE-BGP-TO-EVPN'
```

Importing another VRF's route-target is also what turns on **downstream VNI**
between them. See [DVNI](../../README.md#downstream-vni-dvni) in the top-level
README.

### 6. Routing policy

| Policy | Applied to | What it does |
| --- | --- | --- |
| `local_as_rm` (+ as-path list `local_as_export`, regex `^$`) | Underlay export | Advertise only routes with an empty AS path, which are routes this leaf originated (its VTEP). A leaf never becomes transit between the spines. |
| `PL-<VRF>-L2VNI-SUBNETS` | (prefix list) | The VRF's VLAN subnets, such as `10.6.0.0/16` and `10.8.0.0/16` |
| `RM-<VRF>-CONNECTED-TO-BGP` | Redistributing connected routes | Only the VLAN subnets are let in. In a VRF without VLANs, every connected route is. |
| `RM-<VRF>-BGP-TO-LOCAL-VPN` | VPN export (local leaking) | Same filter: the VLAN subnets, or everything in a VRF without VLANs |
| `RM-<VRF>-BGP-TO-EVPN` | EVPN type-5 advertisement | Permits everything |
| `RM-EVPN-SPINE-EXPORT` | EVPN export to the spines | **Denies type-5 routes for each VRF's own VLAN subnets**, and permits everything else |
| `block_local_as_rm` | (nothing) | Defined, but not applied anywhere |

Hosts in a VLAN are already reachable through EVPN type-2 (MAC/IP) routes, and
every leaf carrying that VLAN has the same anycast gateway subnet. So the leaves
keep their own VLAN subnets out of the type-5 routes they send to the spines.

### 7. System

```text
set system host-name 'LEAF-17'

set system ip multipath ignore-unreachable-nexthops
```

## Before you run it

- The leaf VMs must exist and be running (see [fabric-vms](../fabric-vms/README.md)),
  and the physical leaves must be reachable on their management addresses.
- The VyOS HTTPS API must be enabled on every leaf, with the key in `vyos_api_key`.
- **`ipv4_rt_imports` and `ipv4_rt_exports` must be set on every VRF that a leaf
  receives.** If one is missing, `plan` fails with "Invalid template
  interpolation value".

```sh
tooling/walk-roots.sh fabric-leaves
```

## Things to know

- **The config isn't saved to the boot config.** The leaf resource sets
  `save = false`, while the DHCP VMs use `save = true`. In VyOS, `save` writes
  the running config to `/config/config.boot`. If a leaf needs this config to
  survive a reboot, run `save` on it, or change the flag in
  `modules/fabric/leaf/main.tf`.
- **Check for stale config when you remove or renumber things.** The provider
  sends `set` commands. After removing a VLAN or VRF from the inventory, check on
  the device (`show configuration commands | match <thing>`) that the old config
  is really gone.

## Checking the fabric

Useful VyOS operational-mode commands on a leaf (these are backed by FRR).
Output and availability can vary between VyOS releases:

```text
show bgp summary                          # underlay and overlay sessions
show bgp l2vpn evpn summary               # EVPN sessions to the two spines
show bgp l2vpn evpn                       # the whole EVPN table: type-2 (MAC/IP) and type-5 (prefix) routes
show bgp l2vpn evpn route vni 9008        # EVPN routes for one VNI
show evpn mac vni 9008                    # MACs in a VNI: local, or remote with the VTEP behind them
show vrf vni                              # which L3VNI each VRF uses
show bfd peers                            # BFD status of every session
show ip route vrf lylat_service           # a VRF's routing table
```
